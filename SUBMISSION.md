# FounderFlo Ops — Submission summary

**Problem.** Small businesses run sales and support across Facebook, Instagram, Messenger, and WhatsApp, but the work is manual, scattered, and easy to get wrong: missed inquiries, inconsistent answers, no record of what was sent or why.

**What FounderFlo Ops does.** It is an autonomous business operator for the Meta ecosystem. From one natural-language objective it plans a permissioned workflow, retrieves and classifies customer inquiries, drafts replies grounded strictly in the business's own catalog and policies, creates lead records, drafts promotional content, and — only after explicit owner approval bound to the exact payload — sends and publishes through its platform adapters (a Graph API adapter for Meta's official APIs, and a clearly labelled sandbox adapter).

**Live status, stated plainly.** The Meta AI layer has run live end-to-end: four full operator runs on real Muse models (107–109 live calls each, ≈$1.75–$1.99 at list prices each, receipted). The platform side of those runs used the sandbox adapter. The Graph adapter is implemented and stub-tested, and on 2026-10-27 the production connect flow ran against a real Page: the founder's Floaty Page is live-connected to the hosted deployment through a Meta app registered under the founder's original Facebook account (the first app's account is stuck in a confirmation checkpoint Meta has not resolved), and Meta's debug_token inspection verifies the Page token as valid with all nine requested permissions granted. No post was published and no message was sent during verification; public availability still awaits App Review (Advanced Access) and Business Verification. Verification is per-platform with honest ceilings: Facebook/Instagram/Messenger outcomes are confirmed by reading the object back; WhatsApp exposes no read-back endpoint and tops out at *provider-ID-returned*; an attempt whose outcome is ambiguous stays *unverified* by design rather than being resent or assumed. The owner's activity receipt carries a SHA-256 checksum that detects modification relative to a trusted reference value of the hash — it is not a digital signature, proves nothing about who authored the receipt, and receipts are not cryptographically signed.

**How Meta AI powers it.** Muse Wonder (Meta Model API, Responses API) produces structured, schema-validated plans and drafts; Muse Spark handles lower-cost classification. Model output is treated strictly as proposals: a server-side allowlist, grounded knowledge base, and human approval gate decide what may execute.

**Key innovations.**
- Approval bound to payload hashes — an approval can never be reused for edited content.
- Idempotent execution + a graded verification ladder (request attempted → provider accepted → provider ID returned → object confirmed → published) that never upgrades an outcome beyond its evidence; ambiguous attempts stay *unverified* instead of being resent.
- Prompt-injection containment for untrusted customer text, demonstrated live in the demo data.
- Capability discovery that shows, per account, exactly which operations Meta permissions allow — and why not, when they don't.
- An honest demo architecture: a fully functional sandbox adapter and a clearly labelled deterministic fallback planner, so nothing in the demo is faked — sandbox activity and non-AI planning are identified as such in the UI and in receipts.

**Built new for this hackathon.** The entire codebase (API server, PWA, adapters, engine, tests) was written from scratch for FounderFlo Ops; no existing product code is used.

**Evidence.** A 2:49 demo video (recorded Oct 26, 2026; `~/workspace/metaops-demo/metaops-demo.mp4`) shows a full live-AI operator run against the sandbox storefront — approvals queue, verification, receipt, leads — plus the filmed failure-recovery scene (server killed mid-send at 7 accepted sends with a further send in flight, restarted and resumed with zero duplicate sends) and the edit-after-approval invalidation scene (the edited pending approval was invalidated and replaced under a new payload hash, and the edited text was sent verbatim only after re-approval) — framed honestly as live AI, simulated storefront, real receipts. Its cards and opening narration state it was built with Muse on the Meta Model API for the Meta Global AI Developer Hackathon (Startup Track). The filmed run is receipted: 109 live calls, 168 receipt actions (166 confirmed, 2 auditor-blocked), ≈$1.99.

**Limitations.** Live Graph API use requires Meta app review/permissions per capability; Instagram publishing requires media; messaging windows and opt-in rules apply and are respected, not bypassed. Local persistence is SQLite (Postgres-compatible schema) for the hackathon build. The GitHub repo (github.com/jekayinfa1/metaops-ai, published Oct 26, 2026; currently private at the founder's direction and to be made public again for judging) is a snapshot that **predates** the latest adapter, verification, and security fixes in this working repo — it is not the current code. One UI defect found while filming was fixed on 2026-10-27 (commit ff0671f): the Operator screen's Pause/Resume buttons send an empty JSON body that the server's JSON parser rejected (400), so the filmed pause/resume used the owner's API session on the same endpoints; the API now parses an empty JSON body as {} on all seven affected action endpoints, with regression tests pinning the behavior.

**Naming note.** The developer-console app is named "FounderFlo Ops" (App ID 1671236714578648) — Meta rejected "MetaOps AI" as a console app name. "FounderFlo Ops" is also the approved public-facing product name (founder-approved Oct 26, 2026), developed by FounderFlo LLC; "MetaOps AI" remains the internal working name.

**Theme.** *Push the Frontier:* from chatbots that merely answer, to a supervised operator that plans, asks, acts, verifies, and proves its work.
